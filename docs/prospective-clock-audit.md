# Prospective clock audit — 2026-08-16

Paper 1 concludes that coordination timing cannot be recovered retrospectively
and must be captured prospectively by an instrumented operational system. The
triggers in migration `003_auto_sync_triggers` are that instrument. This is an
audit of whether they actually deliver what the paper says is needed.

Everything below was read from the live database rather than from the repo,
because the question is what is actually running.

## What is running

Five triggers are installed and enabled:

| Trigger | On | Fires |
|---|---|---|
| `trg_case_created_to_research` | `public.cases` INSERT | `FIRST_CONTACT` |
| `trg_case_triage_to_research` | `public.cases` UPDATE | `TRIAGE_COMPLETE` |
| `trg_case_status_to_research` | `public.cases` UPDATE | `TRANSPORT_ACTIVATED` / `DEFINITIVE_CARE_START` / `DISCHARGE` |
| `trg_gop_approved_to_research` | `public.guarantees_of_payment` UPDATE | `GUARANTEED_PAYMENT` |
| `trg_episode_started_to_research` | `public.case_episodes` UPDATE | `FACILITY_ARRIVAL` / `TRANSPORT_ACTIVATED` |

Migration `003` created four of these; `trg_case_triage_to_research` was added
later in `006_case_events_dedup_and_triage`. Each live function body was read
back with `pg_get_functiondef` and matched against its migration, so the repo
and the database are known to agree rather than assumed to.

**The instrument works.** Two `FIRST_CONTACT` events exist with
`actor_id = 'system'` (2026-07-06 and 2026-07-09), generated by real case
creation rather than by backfill. This is the first evidence in the programme
that the prospective path fires end to end.

**Nothing else has fired**, and the reason is benign: `public.cases` holds two
rows, both still `active`. Every status the triggers watch for —
`transport_arranged`, `in_treatment`, `discharged` — is a valid member of the
`case_status` enum, so none of this is dead code waiting to be discovered. The
downstream milestones simply have not been reached yet.

## What the audit found wrong

### 1. `GUARANTEED_PAYMENT` destroyed TTGP at write time — fixed

The trigger read:

```sql
COALESCE(NEW.issued_date::timestamptz, now())
```

`guarantees_of_payment.issued_date` is a **`date`**. The cast lands on midnight,
and because it is the first argument, the `COALESCE` *preferred* that midnight
over the `now()` it already had in hand.

The consequence is exact: time-to-guaranteed-payment — Paper 2's core metric,
and the interval Paper 1 argues most needs measuring — would have been recorded
at day resolution in the new system, for precisely the reason Paper 1 says the
old system failed. It would also have looked like it was working. A populated
`GUARANTEED_PAYMENT` column is indistinguishable from a good one until someone
plots the distribution and finds every value at 00:00.

Nothing had fired (zero rows in `guarantees_of_payment`), so no data was
affected. The defect was latent, which is the only reason this is a note rather
than a retraction.

Fixed in migration 020. The trigger now never silently downgrades: a guarantee
registered today takes `now()` (the moment approval was recorded), and one
back-entered against an earlier date keeps the date **and is labelled as
day-resolution** so no analysis differences it at hour scale.

### 2. Two milestones time the data entry, not the event — labelled

`TRANSPORT_ACTIVATED` and `DEFINITIVE_CARE_START`, when they come from a case
status change, are stamped `now()`. That is a real timestamp, but of the moment
an operator updated the record — not of the moment the ambulance rolled or care
began. If the update lags the event by two hours, the measured interval is short
by two hours.

This is not fixable from inside the research schema, because the operational
tables do not currently carry a departure time on the case row. It *is*
recordable, and migration 020 records it: those events are now labelled `entry`
rather than `measured`, so an analysis can state which it admits.

### 3. The best transport timestamps in the system are unwired

`public.case_transport` carries `actual_departure` and `actual_arrival`, both
`timestamptz`. These are the highest-fidelity transport times anywhere in the
shared database, and **no trigger reads them.** `TRANSPORT_ACTIVATED` comes
instead from a status change (`entry` resolution) or from
`case_episodes.start_date` — and `case_episodes` currently holds zero rows.

Wiring this would require creating a trigger on `public.case_transport`, which
is SOSCOMMAND's table. Migration 003 set a precedent by attaching triggers to
three `public` tables, but SOSPHD's boundary rule is explicit, and adding
behaviour to another project's live operational table is not a decision this
repo should take unilaterally. **Recorded here as a proposed integration
needing SOSCOMMAND's agreement, not as pending work.**

Until then, TTTA measured through the status path carries the `entry` caveat
above.

## What migration 020 adds

`research.case_events.resolution`, an enum on every event:

| Value | Meaning | Usable for an hours-scale interval? |
|---|---|---|
| `measured` | An operational timestamp of when the event happened (`triage_at`, `episode.start_date`, `closed_date`) | Yes |
| `entry` | `now()` at the moment the record was written — a true timestamp, of the entry rather than the event | Yes, with a stated lag |
| `date` | Day resolution only | **No** |

All 844 existing events are classified: 842 `date` (the whole historical
backfill, including the nine transport rows the v0.9 provenance audit
reclassified), 2 `entry` (the live trigger rows — `cases.intake_date` defaults
to row creation, so they time the record rather than the call).

The migration refuses to apply if any row marked `date` fails to sit at midnight
Asia/Bangkok, so the classification is checked rather than asserted.

`research.case_intervals` computes TTTA/TTGP/TTDC and returns **NULL wherever
either endpoint is day-resolution**. Against the current registry it returns 835
rows and zero computable intervals of any kind — Paper 1's central result,
expressed as a query rather than as a sentence. The view is
`security_invoker = true`; without that it would run as its owner and bypass the
SD-001 allowlist on `case_events`.

`scripts/verify-paper-figures.mjs` now asserts all three interval counts are
zero, and that no event is left unclassified. If instrumented data starts
arriving, those checks fail — which is the correct behaviour, because the
baseline paper would then need a stated cut-off date rather than "the whole
registry".

## The through-line

Paper 1 argues that operational records destroy temporal resolution at write
time, and that the fix is to build the clock into the coordination system. This
audit found the replacement clock about to make the same mistake at its single
most important point, and found two more places where it would have reported a
data-entry time as a measurement.

That is not an argument against prospective instrumentation. It is the argument
for instrumenting deliberately: the failure is easy to reproduce precisely
because storing a date where an interval is needed is the natural thing for an
operational schema to do. The defence is that the instrument now records the
quality of its own clock, so the question "is this interval real" is answerable
from the data instead of from memory.
